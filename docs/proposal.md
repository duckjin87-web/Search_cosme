## 1. 제안 요약

1안(제품명 조회 → 채널 이미지 수집 → 면 분류 → 후면 표시사항 체크리스트)을 **사내망 전용 웹 서비스**로 구축한다. Python 백엔드, 작업 큐, PostgreSQL, 이미지 저장소로 구성하고 사내 VM 한 대에 Docker Compose로 배포한다.

- **개발 기간**: 1인 기준 약 12주(추정). 기존 로드맵 순서를 그대로 따르고, 후면 OCR 직후 검증 게이트를 둔다.
- **MVP 채널**: 네이버쇼핑 API 1개와 크롤링 채널 1개(올리브영)로 시작한다. 나머지 채널은 검증 게이트와 법무 검토를 통과한 뒤 어댑터 단위로 붙인다.
- **판정 원칙**: 4상태(있음 / 없음 / 판독불가 / 면 미확보)와 충돌 보존 규칙을 코드 수준의 불변 조건으로 구현한다.

착수 전에 정할 것은 세 가지다. 법무 검토 범위를 Tier 2까지 넓힐지, 외부 OCR·AI API를 써도 되는지, 사내 서버를 받을 수 있는지다. 자세한 내용은 9절에 있다.

## 2. MVP 범위

| 구분 | MVP에 포함 | 이후 단계 |
|---|---|---|
| 채널 | 네이버쇼핑 API, 올리브영 | 화해·컬리·무신사뷰티 → 쿠팡·오픈마켓 → 브랜드 자사몰 |
| 카테고리 | 용기형, 튜브 | — |
| 추출 | 후면 OCR + 상세페이지 텍스트 | 측면 바코드·분리배출 마크 인식 |
| 판정 | 룰셋 9개 항목, 4상태, 충돌 표시 | 법령 개정 알림 |
| 스냅샷 | 수집일별 적재, 기간 조회 | 스냅샷 간 변경 비교 화면 |
| 사용자 | 사내망 접속, 공용 계정 또는 SSO | 권한 등급, 조회 이력 |

네이버쇼핑 API는 상품당 대표 썸네일 한 장과 판매 링크만 돌려준다. 따라서 Tier 1의 역할은 **제품 후보 식별과 전면 이미지**이고, 후면 이미지는 사실상 Tier 2 이상에서만 나온다. 올리브영 어댑터가 MVP에 들어가야 하는 이유다.

## 3. 시스템 구성

```
 사내 사용자 (브라우저)
        │
┌───────┼──────────────── 사내 VM · Docker Compose ────────┐
│       ▼                                                  │
│  [web] 조회부·진행부·결과부                               │
│       ▲ │ 요청 · SSE                                      │
│       │ ▼                                                │
│  [api] FastAPI ──작업──▶ [redis] 작업 큐                  │      사내망 밖
│       │ 캐시 조회              │                          │
│       ▼                        ▼                          │
│  ┌ 저장소 ─────────┐  ◀─이미지─ [worker-collect] ─────────┼──▶ 판매 채널
│  │ postgres        │            채널 어댑터                │    (네이버 API, 올리브영)
│  │ minio (이미지)  │                 │                     │
│  └─────────────────┘  ◀─판정── [worker-vision] ──────────┼──▶ OCR · LLM API
│                                 면 분류 → OCR → 4상태 판정│
└──────────────────────────────────────────────────────────┘
```

조회 요청은 캐시(postgres)에서 바로 답하고, 캐시에 없는 부분은 작업 큐에 넣어 워커가 채운다. 수집 워커와 판독 워커를 나눈 이유는 부하가 다르기 때문이다. 브라우저 수집은 메모리를, OCR은 연산과 외부 API 비용을 쓴다.

## 4. 기술 스택

| 영역 | 선택 | 이유 |
|---|---|---|
| API 서버 | Python 3.12, FastAPI | 비동기 처리, 수집·OCR 라이브러리와 같은 언어 |
| 백그라운드 작업 | Celery + Redis | Tier 2~4 수집을 비동기로, 채널별 큐로 호출 간격 제한 |
| 수집 | Playwright(헤드리스 브라우저), httpx | 스크립트로 그리는 상세페이지 대응 |
| DB | PostgreSQL 16 | 스냅샷·판정 관계형 저장, OCR 원문은 JSONB |
| 이미지 저장 | MinIO(S3 호환) 또는 사내 NAS | 레포·DB 밖에 보관, 해시를 파일 키로 써서 중복 제거 |
| 면 분류 | 비전 지원 LLM API, 제로샷 분류 | 학습 데이터 없이 시작. 게이트에서 정확도 미달 시 전용 분류 모델 학습 |
| OCR | 후보 3종 비교: CLOVA OCR, Google Cloud Vision, PaddleOCR(사내 구동) | 한글 소형 글자 성능을 게이트에서 실측해 선정 |
| 항목 분해 | 키워드 룰 + LLM 보조 | OCR 텍스트를 9개 항목으로 나눔 |
| 룰셋 | YAML 파일, Git 버전 관리 | 코드와 분리 (ruleset.md 원칙) |
| 화면 | React(Vite) SPA, 진행 상태는 SSE | 채널별 수집 상태를 실시간 반영 |
| 배포 | Docker Compose, 사내 VM 1대 | MVP 규모에 충분, 운영 부담 최소 |

**OCR 엔진 선정의 필수 조건은 단어별 신뢰도를 돌려주는가다.** LLM에 이미지를 바로 넣어 항목을 뽑으면 "못 읽음"과 "없음"을 가를 근거가 남지 않는다. 따라서 글자 인식은 OCR 엔진이 하고, LLM은 면 분류와 항목 분해에만 쓴다.

## 5. 모듈 설계

### [1] 채널 어댑터

```python
class ChannelAdapter(Protocol):
    channel: str            # "oliveyoung"
    tier: int               # 1~4
    min_interval_sec: float # 채널별 호출 간격

    async def search(self, query: str) -> list[Candidate]: ...
    async def fetch(self, c: Candidate) -> RawPage: ...
    # RawPage = 이미지 URL 목록 + 상세 텍스트 + 원본 URL + 수집 시각
```

- 실패는 채널 단위로 격리한다. 한 채널이 막혀도 나머지 결과는 그대로 나간다.
- 어댑터마다 최근 성공률과 마지막 성공 시각을 기록한다. 연속 실패가 일정 횟수를 넘으면 자동 비활성화하고 알린다.

### [2] 면 분류

- 출력: `front | back | left | right | top | bottom | lifestyle | other` + 신뢰도, 그리고 용기형·튜브 판별.
- 국내 상세페이지는 여러 컷을 이어 붙인 **세로로 긴 이미지 한 장**인 경우가 많다. 분류 전에 컷 단위로 자른다.
- 신뢰도가 낮은 이미지는 면에 배치하지 않고 미분류로 보관한다.

### [3] OCR·추출

- 후면 이미지 → OCR(단어 + 신뢰도 + 위치) → 항목 분해 순으로 처리한다.
- 상세페이지 HTML 텍스트와 상세 이미지 안 글자는 `detail_text` 경로로 따로 추출한다.
- 두 값은 공백·구두점·괄호를 정규화한 뒤 비교하고, 다르면 `conflict: true`로 양쪽을 보존한다.

### [4] 룰셋 판정

```yaml
version: 0.1
items:
  - id: ingredients
    name: 전성분
    basis: 화장품법 기재사항
    faces: [back]
    keywords: ["전성분", "전 성분", "성분명"]
  - id: lot_position
    name: 제조번호 표기 위치
    faces: {container: [bottom], tube: [bottom]}  # 튜브는 씰링부
```

항목마다 아래 순서로 판정하고, 먼저 맞는 조건에서 멈춘다.

1. 어느 소스에서든 값을 찾음 → `ok`. 후면 없이 상세 텍스트로만 찾았으면 note에 "상세 텍스트 기준"을 남긴다.
2. 항목의 주 확인 면이 미확보 → `face_missing`.
3. 면은 있으나 OCR 신뢰도가 기준값 미만인 영역이 있음 → `unreadable`.
4. 면 전체가 기준 이상으로 읽혔는데도 없음 → `none`.

`none`은 "다 읽었다"는 증거가 있을 때만 나온다. 애매하면 `unreadable`로 기운다.

## 6. 데이터 모델

| 테이블 | 주요 컬럼 | 역할 |
|---|---|---|
| `products` | product_key, brand, name, volume, barcode, category | 매칭 키 = 브랜드 + 제품명 + 용량, 바코드 있으면 우선 |
| `listings` | product_key, channel, source_url, title_raw, matched_by | 채널별 상품 페이지. 채널 표기 원문 보존 |
| `snapshots` | snapshot_id, product_key, collected_at | 수집일 단위 묶음. 기간 조회의 기준 |
| `images` | image_hash, storage_key, width, height, source_channel, source_url, collected_at | 해시가 기본키 → 같은 이미지는 한 번만 저장 |
| `faces` | snapshot_id, face, status, image_hash, ocr_confidence, is_representative | 면별 확보 매트릭스. 대표 1장 + 보조 여러 장 |
| `checks` | snapshot_id, item_id, status, value, source, conflict, note, ruleset_version | 항목별 판정. 어느 룰셋 버전으로 판정했는지 기록 |
| `check_values` | check_id, source, channel, value_raw | 충돌 시 양쪽 값을 모두 보존 |
| `collect_jobs` | job_id, query, channel, status, error, started_at, finished_at | 진행부 화면과 어댑터 모니터링의 근거 |

`checks`에 `ruleset_version`을 남기는 이유는 스냅샷 비교 때문이다. 값이 바뀐 것인지 판정 기준이 바뀐 것인지 구분할 수 있어야 한다.

## 7. API와 화면

| 메서드·경로 | 용도 |
|---|---|
| `POST /api/lookups` | 제품명·기간·카테고리로 조회 시작. 캐시 결과 + 수집 작업 ID 반환 |
| `GET /api/lookups/{id}/events` | 채널별 상태(대기 / 수집 중 / 완료 / 실패) 실시간 스트림 |
| `GET /api/products?q=` | 제품 후보 목록. 매칭이 모호할 때 사용자가 선택 |
| `GET /api/products/{key}/snapshots` | 수집일 기간으로 스냅샷 목록 |
| `GET /api/snapshots/{id}` | 면별 확보 현황 + 체크리스트 |
| `GET /api/snapshots/compare?a=&b=` | 두 수집일의 표시사항 차이 (6단계) |
| `GET /api/images/{hash}` | 이미지 열람. 사내 인증을 거친 요청에만 제공 |
| `GET /api/admin/adapters` | 어댑터별 성공률·마지막 성공 시각 |

화면은 기획안 7절을 따르되 두 가지를 더한다.

- 제품 매칭이 모호하면 조회부 다음에 **후보 선택 단계**가 끼어든다. 기획세트·증정·리필이 섞이기 때문이다.
- 체크리스트의 각 항목에서 근거 이미지와 원본 URL을 바로 본다.

하단 고정 안내 "사전 참고용 · 최종은 실물·도면 확인"은 모든 결과 화면에 둔다.

## 8. 배포·운영

| 항목 | 제안 |
|---|---|
| 서버 | VM 1대, 4 vCPU · 16GB RAM · 디스크 500GB (시작값, 게이트 후 재산정) |
| 컨테이너 | web(nginx + 화면), api, worker-collect, worker-vision, postgres, redis, minio |
| 접근 | 사내망 전용, 외부 공개 없음. 로그인은 사내 SSO 연동(불가 시 공용 계정) |
| 외부 통신 | 나가는 방향만: 수집 채널, 네이버 API, OCR·LLM API. 방화벽 허용 목록 필요 |
| 비밀값 | API 키는 서버의 `.env`에만 둠. 레포에는 `.env.example`만 |
| 백업 | PostgreSQL 일 1회 덤프, 이미지 저장소는 NAS 스냅샷 |
| 모니터링 | 어댑터 상태 화면 + 연속 실패 시 메일 또는 Teams 웹훅 알림 |
| 보존 기간 | 수집 이미지 보관 기간은 법무 검토 결과에 맞춘다 |

`main`에 합치면 GitHub Actions가 테스트와 이미지 빌드를 하고, 사내 서버에서 `docker compose pull && up -d`로 반영한다. 자동 배포를 원하면 사내에 셀프 호스티드 러너를 둔다.

## 9. 검증 게이트 기준 (제안)

| 지표 | 정의 | 제안 기준 | 미달 시 대응 |
|---|---|---|---|
| 면 분류 정확도 | 면 라벨이 정답과 같은 이미지 비율 (후면 기준 별도 집계) | 90% 이상 | 전용 분류 모델 학습, 또는 사용자가 면을 직접 지정 |
| 후면 항목 판독률 | 후면 6개 항목 중 값을 맞게 읽어낸 비율 | 70% 이상 | 상세 텍스트를 주 소스로 전환 (로드맵 대응안) |
| 누락 오판율 | 실제 표기가 있는데 `none`으로 판정한 비율 | 1% 이하 | `none` 판정 임계값을 올려 `unreadable` 쪽으로 기울임 |

- 샘플 40개(용기형 20, 튜브 20). 정답지는 실물 또는 사내 도면 기준으로 사람이 만든다.
- OCR 엔진 선정도 이 단계에서 한다.

## 11. 선결 과제와 의사결정 요청

- [ ] **법무 검토 범위에 Tier 2 포함** — 로드맵은 Tier 3~4만 검토 대상이지만, 올리브영 등 Tier 2도 크롤링이라 약관 문제가 같고 MVP에 포함된다.
- [ ] **외부 OCR·AI API 사용 승인** — 안 되면 PaddleOCR 사내 구동, GPU 서버가 필요할 수 있다.
- [ ] **사내 서버 확보** — VM 1대와 방화벽 아웃바운드 허용.
- [ ] **네이버 검색 API 키 발급** — 네이버 개발자센터 애플리케이션 등록.
- [ ] **검증 게이트 기준값 확정** — 90% / 70% / 1% 수용 여부.
- [ ] **샘플 40개와 정답지 담당자 지정** — 실물 또는 도면을 볼 수 있는 사람.
